# Independent file manager extension

This document describes the current file-extension source contract, including the shared workspace and allowed-directory configuration introduced in 2.0.2. Windows native terminal and eligible Windows Docker Desktop Linux-container extension support are included in staff-mcp 2.0.4, not 2.0.3; extension protocol versions are unchanged. Reverse and extensions require a matching chat-ai host implementing reverse v1 and session-relative data paths, with matching host/descriptors/UI assets. The authoritative protocol is `chat-ai/docs/protocol/README.md` at that compatible host version; both endpoints implement it themselves, with no required extension SDK. Standard stdio/Streamable HTTP tools/resources/prompts remain supported. No Chat8/schema9/format7/share protocol2 data migration is required. See [compatibility and upgrade](../README.md#compatibility-and-coordinated-upgrades).

The no-port stdio data changes on this branch are **unreleased** and require paired host/development artifacts (`2.0.7-dev.0` for local integration). They are not supplied by the default registry 2.0.6 bundle and do not imply a published 2.0.7.

Extensions are off by default. Unsupported versions, unavailable optional features or failed data setup leave an otherwise healthy standard MCP connection usable, without enabling the affected App. This does not make the old reverse handshake compatible: reverse requires a paired upgrade even when extensions are disabled, with no old-protocol fallback or automatic transfer resumption.

Requires Node.js 22.22.2 or newer on the host and in Docker. Current source supports native Windows extensions and eligible Windows Docker Desktop Linux containers, subject to per-feature prerequisites. Docker preflight checks the Linux-container daemon OS, not the launcher OS; HTTP/stdio also require a verified local Unix socket or named-pipe (`npipe`) endpoint. Windows containers are not supported for extensions. Native terminal needs Windows build >= 18309 and a loadable ConPTY dependency, not merely a file UI that opens. Windows arm64 and macOS are not hardware-validated; musl/Alpine terminal support is not promised.

## Tools, file apps, and Resources

- **Tools** retain their existing MCP names and `tools/call` behavior. A host must not infer a file app from tool metadata or wrap file-manager requests as tool calls.
- **File apps** are advertised by an experimental initialize capability. The host reads the declared HTML Resource and supplies a restricted bridge for direct user operations; no model invocation is required.
- **Resources** use standard MCP list, template, read, subscribe, and unsubscribe methods. Non-UI file Resources work without app negotiation: when files is enabled they use the configured file-app roots; otherwise they retain the standard workspace/allowed-directory scope. UI Resources require the corresponding enabled and negotiated app capability.

The initialize capability uses one discovery root:

```json
{
  "experimental": {
    "cc.qqxing/extensions": {
      "version": 1,
      "extensions": {
        "cc.qqxing/apps": { "versions": [1] },
        "cc.qqxing/files": { "versions": [1] },
        "cc.qqxing/data": { "versions": [1] }
      }
    }
  }
}
```

All extensions are disabled by default. The manifest above applies when files is explicitly enabled; a usable, explicitly enabled Linux/Windows PTY adds `cc.qqxing/streams: {versions:[1]}` (not a terminal manifest entry). Apps/data dependencies are derived automatically from enabled, available features; terminal alone does not enable files. Disabled features register no corresponding business handlers or UI Resources. With all extensions off there is no extension manifest, app/data handler or application data listener/session; ordinary tools and non-UI Resources remain. If the explicitly requested terminal's platform/native PTY/shell requirements are unavailable, startup fails even when files is also requested; terminal/streams are not silently omitted. With terminal disabled, native PTY code is not loaded. Files-only optional-extension degradation is unchanged. Negotiation is tied to the actual initialized SDK session, not a client name. Calls to `cc.qqxing/apps/v1/list {}` return `{apps:[...]}`. The `files` descriptor uses `ui://staff-file-manager/v1/index.html`, `mimeType:"text/html"`, `bridgeVersion:1`, `icon:"folder"`, `requiredExtensions:{"cc.qqxing/files":1,"cc.qqxing/data":1}`, and the ordinary `cc.qqxing/file-manager/*` methods listed below. It declares `capabilities.files:{version:1,upload:true,download:true}`; file lifecycle methods are owned by the files module, not descriptor-provided method mappings.

Old `experimental["cc.qqxing/apps"]`, `cc.qqxing/file-transfer/*` and private FTE chunks are not aliases or fallbacks; no backend MCP WS data path remains (the independent browser App stream WS is not a fallback). Ordinary tools and standard non-UI Resources do not require app negotiation; they remain available without granting implicit file-app or terminal access. A files manifest alone does not provide a binary path: negotiate data v1 and configure the current connection dataSession. Local stdio/Docker use bounded same-connection Base64 frames; direct HTTP/reverse retain raw HTTP, with the same consumption-ACK semantics; unsupported extensions do not affect standard MCP clients.

## App and bridge boundary

The app is served by standard `resources/read` at the declared UI URI. It is not a hosted web URL and is not included in ordinary file resource listings. The current chat-ai host reads that HTML through its SDK, runs it in an opaque-origin `sandbox="allow-scripts"` iframe, blocks network access with CSP, and uses a source-checked MessageChannel handshake. Theme and enabled/connected lifecycle messages come from the host. The theme snapshot includes semantic colors, font families, base font size, and control radius; the app accepts a property-typed allowlist on the authenticated port. Toolbars, tabs, editor surfaces, and progress indicators use those tokens. This does not enable network access or load the host’s external web fonts; font families use locally available fallbacks.

The direct file-manager namespace is `cc.qqxing/file-manager/`. Its ordinary methods are `roots`, `list`, `stat`, `readText`, `saveText`, `createFile`, `mkdir`, `move`, and `delete`. Transfer preparation, finalization, and release are separate methods controlled by the host. The bridge is a generic app host, not an arbitrary tool executor, fetch proxy, shell, or filesystem API. The app translates file actions into its declared full method names; chat-ai does not interpret root/path/editing business parameters. The `mcp-app-ready` / `mcp-app-connect` handshake binds a private MessagePort. Separate app IDs on one MCP are independent launchable workspaces; transport extensions are not UI applications.

## Lazy directory tree

The file navigator uses an on-demand tree for the currently selected root. Opening the app loads only the root’s first page (100 entries); expanding a folder lists only its direct children. Each folder owns its cached pages, loading/error state, cursor, and “Load more” action. After merging pages, the UI sorts that directory’s complete set of loaded entries with directories first and names ascending within the directory and non-directory groups; symlinks remain non-directories. Rendering and keyboard navigation use that same order. The server still paginates by name: until all pages are loaded, the visible entries are not guaranteed to include every directory, and loading another page may insert directories ahead of already-visible files. Sorting does not trigger extra metadata/text reads or fetch unrequested pages. Collapsing a branch hides its descendants without closing file tabs or discarding editor drafts, and reopening an already-loaded branch reuses its cache. No background traversal, eager document reading, filesystem watcher, or full-project index is started.

The tree cache is scoped to the current root and connection availability. Pending reads are fenced when that scope changes or a directory is invalidated, so late replies cannot repopulate an old branch. A failed folder can be retried independently. If the server rejects an expired cursor, that folder must be refreshed rather than appending an inconsistent page. Caches and expansion are not persisted across browser reloads.

The toolbar breadcrumb identifies the current directory, which is the destination for blank-area creation and upload actions; a directory context menu instead targets that directory. There is no separate target-description row. Refresh is an icon in the same toolbar. File names appear in the tree and editor tabs; their full path and listing metadata are available in tooltips instead of repeated headings, an editor-path label or a persistent selection footer. Selecting a folder chooses that folder; selecting a file or activating its editor chooses its parent. Refresh reads that directory’s first page again, resetting only its pagination rather than reloading the entire tree. Save/create/upload refresh their affected parent; rename/move refresh the source and destination parents already loaded by the tree and discard obsolete subtree caches; deletion clears the removed branch and moves an affected destination back to its parent. Open tabs still use their existing version checks, path updates, and draft confirmations. Upload completion refreshes the original upload destination even if navigation changed meanwhile.

On wide views (at least 900 CSS pixels inside the app), the tree and file content appear side by side. Narrow views and phones switch between the tree and content, keeping the same open tabs. Arrow keys move through visible nodes, right/left expand or collapse, and Enter/Space open or select; the existing context-menu key and Shift+F10 continue to work. Activating a tab can expand its ancestors, but never automatically consumes every pagination cursor to locate an item.

The UI renders only expanded branches. Its cost still grows with explicitly loaded, visible entries; this is not a virtualized million-file explorer. The existing server listing implementation reads and sorts a directory’s names before slicing a page, so pagination bounds response size, not the total work of enumerating an exceptionally large single directory. The tree does not change that backend contract or claim to improve network bandwidth. Markdown files now offer an explicit Edit/Preview switch over the current text draft; drag-and-drop moves, Git decorations and recursive search are still outside this UI.

## File actions and adding to a conversation

Tree rows and blank space open contextual menus through desktop right-click, touch/pen long press (about 500 ms), or the keyboard context-menu key / Shift+F10. A hold is cancelled by movement beyond 10 CSS pixels, scrolling, pointer cancellation, navigation, lifecycle changes, or unmounting. It does not prevent ordinary taps or scrolling. After a successful hold only its following synthesized click is consumed; a new physical gesture and keyboard activation are unaffected. The menu supports keyboard navigation and Escape, stays within the iframe viewport, and closes on navigation, scrolling outside the menu, resize, or lifecycle changes. Actions bind to the row that opened the menu, not a previous selection. There are no row “⋯” buttons, tree-local current-directory “⋯”, global file-operation menu, or persistent bottom selection summary. Hover details use the listing metadata; selecting a row does not issue an extra metadata-only stat request. Mutation actions still fetch the latest version before opening their confirmation dialog.

The menu entry points for creating a file/folder, uploading files or choosing a folder upload are directory and blank-area tree context menus. A directory row targets that directory; blank space targets the current breadcrumb directory, including at an empty root. File menus retain their file operations. Transfer history is app-wide, not scoped to a tree location: a dedicated transfer icon beside the toolbar refresh button opens or collapses the existing drawer, including when the directory is empty, read-only, or disconnected. It is not offered in tree context menus. The drawer retains records across directory navigation, its progress/attention indicators, and its existing clear/close actions. The toolbar retains navigation, refresh, and this global transfer control, not create/upload controls. Upload selection captures its root and directory before opening the device picker: changing the selection or current directory while the picker is open cannot redirect the files. A changed root/connection lifetime rejects the old selection instead of reusing stale scope. Read-only/unavailable destinations remain blocked.

The focusable tree also accepts paste events containing actual browser `File` objects. Selecting a directory targets it, selecting a file targets its parent, and an unselected tree targets the current directory. Plain text and pastes into the editor, inline name fields, or other editable elements are not intercepted. FileList and clipboard items are alternate representations, not two upload batches: the populated FileList is preferred, with items as fallback, and duplicate object references are removed without merging distinct same-name files. Default screenshot names such as `image.png` and empty names receive timestamp/random names with an extension; ordinary named files retain their names. No asynchronous clipboard permission API is used, and a paste without file objects never creates an upload or reports success.

External file drops upload only within the tree. A directory row targets that directory, a file row targets its parent, and blank space targets the current directory; a lightweight row/background highlight marks the physical drop location. The target is resolved directly from the drop event, never by changing selection and reading it later. Folder paste/drop payloads are rejected without recursively scanning their contents. Outside the tree, external file drops are prevented from navigating the browser and do not start uploads; ordinary editor text dragging remains available. Picker, paste, and drop all use the existing upload queue, overwrite/version confirmation, cancellation, and refresh of the original destination after completion, even after navigation. Actual uploads expand the existing transfer drawer. None of these inputs broadens the iframe sandbox or changes the bridge/transfer protocol.

New files and folders share an inline name field under the target tree directory, labeled “文件名” for files and “文件夹名” for folders. Only the name is requested: Enter or the explicit Create button confirms, Escape cancels, and IME composition must not submit early. These actions use button clicks and an explicit Enter handler, not form submission, because the iframe does not allow forms. The destination root/directory is captured when naming starts; navigation, root or lifecycle changes cancel the naming UI rather than redirecting a late action. Pending submissions are guarded against duplicate Enter/click requests, and late replies cannot change a newer naming operation.

Creating a file immediately calls the existing atomic `createFile` with empty text; folders use `mkdir`. Existing names are rejected, never overwritten. Success refreshes only the original parent directory and does not open an editor or create an unnamed tab. Users click the created file later to open, edit and save it with the existing version-checked `saveText` flow. All file tabs represent existing server files; unsaved edits keep their existing dirty/close/leave protections. File/folder creation does not add a new backend API or persist browser drafts across reloads.

Open, download, rename, move, copy path, and delete keep their existing business checks. Mutations still fetch a version for the intended target and use the same confirmation flow; deletion is not performed by opening the menu. Directories do not expose file attachments; they can explicitly download a ZIP archive. Symlink restrictions remain unchanged.

Regular files offer **Reference file** by default and a separate **Attach content** action for files within the content budget. Both use the canonical `staff-file://` Resource URI with each literal path component encoded once and the generic bridge `attachResource { uri, title, mode:"reference"|"content" }`. Reference mode does not read the file body, so a large file can still be named in a conversation; the compatible host retains the source metadata in the submitted message and clearly marks it as reference-only. A reference is not a content snapshot, a new tool grant, or proof the file still exists. Content mode still reads the actual Resource with the independent 256 KiB limit, preserving its source alongside the snapshot. Neither action sends a model message automatically.

If an open tab for that file has unsaved changes, either action is blocked with a save-first message; the app never silently saves or attaches an older disk copy. The host composer remains the authority for current attachments. Older hosts which do not understand `mode` must be upgraded together, not silently treated as if a reference included file content.

## Resizable desktop panes

On wide layouts, drag the divider between the file tree and editor with the mouse to resize both panes. Pane minimums prevent either side from disappearing; resizing the host window clamps the visible width without changing file tabs or drafts. The setting lasts for the current open App instance and is not stored across users or servers. Narrow layouts retain the existing file/editor navigation instead of displaying a draggable divider. The focused divider also supports arrow keys and Home/End; double-click resets its default width.

## Markdown and directory transfers

A structured `BINARY_FILE` refusal from `readText` is a normal unsupported text-preview result: the UI keeps a neutral placeholder, download and reference actions, without a red MCP error. Other size/encoding failures and real authorization, missing-file or connection errors remain visible; classification never guesses from an error-message substring or filename alone.

`.md` and `.markdown` text tabs provide Edit and Preview modes. Preview uses the current unsaved draft, supports GFM tables/lists/code, and never saves as a side effect. Raw HTML is not executed, images are not fetched, and links do not open arbitrary network destinations from the isolated App. Text size and file save/version checks are unchanged. Video/audio streaming, Range downloads and transcoding are not included.

**Upload folder** uses the browser directory picker and preserves each selected file's relative path. It validates components, creates required directories, then uses the existing bounded per-file upload queue and overwrite/version confirmation. Browser directory selections do not represent empty directories; empty-folder preservation is not promised. Folder paste/drop is still rejected rather than silently uploading a partial tree. Root/connection changes fence a pending picker, and no operation gains access outside the selected file root. This is not an all-or-nothing batch: cancellation or a later failure does not remove already-created directories or committed files.

**Download ZIP** requests read prepare with `archive:"zip"` for a selected non-root directory. The service streams an archive into its private staging directory, keeps relative names and empty directories, and then exposes the ordinary prepared snapshot with a `.zip` filename. It does not buffer the tree or ZIP in the browser and does not run a shell archiver. Symlinks, protected staging, unsupported objects or detected tree changes fail preparation instead of being silently omitted; this is not an atomic filesystem snapshot. The existing preparation timeout, lease and available staging disk limits still apply, so exceptionally large/slow directory preparation may fail explicitly.

A download click now prepares, acknowledges and hands off to the native browser download manager automatically. A manual-start action is offered only when the host confirms the original handle was not consumed; it must never replay an already-started stream. Completion reports host-verified bytes, not proof of local disk persistence. Progress-query retries are read-only and do not restart a download.

Transfer records keep two active slots and at most 128 heavyweight/unresolved records. A confirmed terminal operation moves to compact history only after staging cleanup succeeds; the combined cap is 4096. Original idempotency fingerprints, commit receipts and the five-minute retention window remain intact, queries do not renew that window, and uncertain publication is not evicted as a failed write. Capacity exhaustion still fails explicitly.

## Roots, paths, and concurrent edits

Files is enabled by `--extensions files` (or `--extensions files,terminal`). File roots reuse standard tool authorization: `main` is the workspace, followed by resolved, deduplicated `--allowed-dir` directories in order as `extra1`, `extra2`, etc. Explicit `-d` authorization is visible in the UI; relative directories resolve from the launching process cwd. The `rootId` RPC interface is unchanged; IDs are derived from the current ordered configuration, not user-selected or portable permissions. The programmatic `ExtensionOptions` now contains only `enabled`; there is no independent `fileRoots` option.

No system root is authorized automatically. Explicit `-d /` authorizes the filesystem visible to staff for both tools and files, subject to OS permissions. Docker reuses only the existing workspace and allowed-directory mounts, not separate file-root mounts; explicit host-root authorization is deliberately broad and remains subject to Docker topology and permissions. Terminal still starts at the workspace. File/path guards are not a machine-wide boundary against an arbitrary same-user shell. Removed CLI options fail as unknown options; see [CLI changes](../README.md).

Docker uses the same allowed-directory mounts for tools and files. Host filesystem roots map to `/opt/staff-allowed/root-N`, never container `/`; Windows drive/UNC allowed directories are translated into the POSIX container namespace. Inner allowed directories and protected staging aliases follow the same mapping, including overlapping mounts: Windows path translation does not bypass staging protection or add authorization.

Public paths are root-relative literal names, not host absolute paths or URL-encoded paths. Traversal, symlink traversal, protected roots, and private staging access are checked by the file core. Percent signs in RPC paths are literal filename characters; only the resource URI boundary decodes each component once. Root IDs are session/configuration context, not portable filesystem permissions.

Text reads default to **2 MiB**, and edits/saves remain capped at **2 MiB**. The file App first calls metadata-only `stat`: files up to **512 KiB** open directly, while files above **512 KiB** and below **5 MiB** show their size and a **Load text** button before reading any body or preparing a snapshot. File kind is not guaranteed by an extension: the button attempts UTF-8 text reading, and `BINARY_FILE` keeps the neutral unsupported-preview placeholder. Files **5 MiB or larger** are download-only for text; existing raster-image previews keep their independent 2 MiB budget.

The existing `readText` RPC accepts optional `maxBytes`, an integer from 1 through **5 MiB - 1 byte**, defaulting to the original 2 MiB. The core rechecks actual opened-file size and consistency during reading; a small file that grows past the automatic budget returns to manual confirmation instead of auto-retrying. An explicitly loaded document up to 2 MiB is still editable when the root permits it; larger text is read-only, with save/undo/redo disabled and no Markdown rendering. Large documents skip syntax parsing and mobile line wrapping. Loading is deduplicated per tab; closed tabs or invalidated operations do not receive late content, and switching back to a loaded tab does not reread it.

Near-limit RPC results are checked against a **10 MiB - 64 KiB serialized-result budget**, reserving room within the SDK stdio buffer for the JSON-RPC envelope. Escaping-heavy text that exceeds this budget returns a diagnostic `TOO_LARGE` and retains download rather than disconnecting stdio; this guard does not enlarge host/SDK limits. Model `read_file`, standard Resource/content attachments (256 KiB), image bytes, and write limits are unchanged; preview never automatically attaches body text to the model.

`saveText` requires the version returned by the read; overwriting an existing upload target likewise requires `expectedVersion`. Shared file-core operations serialize supported writes, recheck versions before publication, and use atomic publication rather than editing a target incrementally. `VERSION_CONFLICT` preserves the editor draft; the UI does not silently force an overwrite. These checks are not a promise to sandbox arbitrary external processes with access to the same filesystem.

`stat` returns metadata without reading/hashing file content by default. Call `stat` with `includeVersion: true` only when a mutation needs a content version; `readText` returns the version along with text. File selection/opening must not hash a large binary merely to display its name. Atomic replacements preserve the target permission bits, including executable bits. Upload copy and download snapshot/hash happen outside the shared write mutex; bounded final source/destination checks remain coordinated. External writers are detected through the documented version/identity checks, not locked out by this service.

Private staging is under the workspace's `.staff/file-manager/`; supported file tools and extension browsing exclude/protect that area. The Docker wrapper also derives its aliases from the bind mounts it creates, including overlapping allowed directories: aliases cannot be read, written, listed, moved or deleted through file APIs, and their ancestors cannot be moved or deleted. A root mounted from within staging is protected in its entirety. This is a path guard for wrapper-owned mounts, not a general bind-mount or OS isolation mechanism; arbitrary extra `-D` mounts and same-user shell access are outside that guarantee. Do not treat staging files or transfer handles as user attachments or ordinary Resources.

## Standard file Resources and attachments

`resources/list` publishes root manifests and immediate regular files at each root, with pagination. It is not a recursive index of all descendants. `resources/templates/list` publishes `staff-file://<rootId>/{+path}` templates for nested paths. A URI encodes each path component once; the server checks canonical encoding and root-relative path validity.

`resources/read` returns real text, Base64 blob content, or a directory manifest. A directory manifest follows the file listing contract, including any next cursor; it is not a recursive archive. The server caps each resource at **256 KiB**, explicitly rejects excess data, and does not truncate. Subscriptions notify clients of changes made through the shared file core; this is not a general filesystem watcher for every external edit.

In chat-ai, adding a file is an explicit action inside the app, without a separate resource workspace. Reference mode records only the source URI and metadata, clearly marked as unread; content mode retains a snapshot of the returned contents. Text uses the existing text ContentPart; supported image blobs use data URLs and image ContentParts; other blobs use existing file ContentParts. On send, a text source marker with structured `resource` metadata preserves the MCP identity, URI, name, mode and timestamp in the formal message; any content snapshot follows it. Source metadata also travels through history, Fork, sharing and export, so shared/exported messages include those user-selected names and URIs. Existing messages remain readable, but older strict host versions may reject the new optional field; rollback is not automatically lossless. The host checks the aggregate decoded content limit of 256 KiB for content mode and excludes `ui:` and declared app HTML in both modes. Browsing does not invoke a model or automatically save a message.

## Authorization and cross-chat lifecycle

staff-mcp enforces its configured file-path boundaries and per-session negotiation, not an OS sandbox around arbitrary same-account processes. It does not interpret chat-ai user roles or chat IDs. A host must enforce its own user identity and current grant before dispatching requests.

The current chat-ai integration uses the authenticated physical user namespace, reads persisted current-chat grants on each operation (including inherited role settings), and uses persisted user defaults for the home/new-chat scope. Runtime bindings include the exact SDK server instance, connection UUID/generation, and app descriptor. Reconnecting invalidates old references, even if the configured server name is unchanged.

The host keeps the iframe mounted across chat routes so in-memory tabs and unsaved drafts can survive a chat switch. An app is not permanently bound to its first chat; reuse still requires the new chat's current permission for the same connection. The current UI cancels active transfers when switching scopes or losing permission/connection rather than promising transparent cross-chat continuation. Apps without the current chat’s MCP grant are hidden from the launcher and workspace, while their iframe drafts remain mounted in the background. Returning to an authorized chat restores access to those drafts. Authorized but disconnected apps can still display drafts for copying, without writing through stale references. Refresh, browser exit, and process restart do not restore drafts or resume transfers.

Cleanup is deliberately narrower than file access: an owner can cancel/close their existing app's temporary transfers even after the grant is revoked, without gaining a new read, write, or commit permission. chat-ai expires idle app bindings after two hours and idle transfers after five minutes.

## files v1 prepared transfers over a shared dataSession

The file app and chat-ai's existing `transfer_file` tool share `cc.qqxing/files/v1/*`, not separate app and FTE lifecycles. Ordinary file CRUD retains its existing namespace and schemas. Current staff handlers strictly validate the remote business parameters:

| Method suffix | Parameters | Result / meaning |
| --- | --- | --- |
| `roots` | `{}` | configured logical roots |
| `resolve` | `{uri}` | `{rootId,path}` after validating a local `file://` URI against those roots |
| `prepare` (read) | `{operationId,mode:"read",rootId,path,archive?:"zip"}` | stable file snapshot or explicit non-root directory ZIP |
| `prepare` (write) | `{operationId,mode:"write",rootId,path,size,sha256?,overwrite?,expectedVersion?}` | private staging; overwrite defaults false, true requires expectedVersion, false forbids it |
| `commit` | `{operationId,transferId,sha256}` | committed result `{path,size,sha256,version}` or the operation's current state |
| `status` | `{operationId}` | bounded state/result lookup, never resumes a transfer |
| `renew` | `{operationId}` | `{operationId,expiresInMs:30000}` |
| `cancel` / `release` | `{operationId}` | shared cleanup; `TOO_LATE` after commit admission |

The host generates operationId before the first asynchronous prepare. Prepared metadata includes `operationId,transferId,state,loaded,name,size,expiresInMs,recordTtlMs`; reads also return `sha256,version`. The request field is **mode**, not direction; the lease field is **expiresInMs**, not leaseMs. Reads reject write-only fields. Same operation and parameters deduplicate within that live session; changed parameters or commit digest produce `IDEMPOTENCY_CONFLICT`. Cleanup before a delayed prepare leaves a bounded cancellation tombstone.

The host bridge preserves authorization, owner/connection identity, quotas, leases, commit/status and stable rootId/path, size/sha256, overwrite/expectedVersion validation. It removes maxBytes from remote prepare and enforces it as a host receive budget; mode and operationId are overridden last by the host. Other flat business prepare parameters pass through to the original peer, without a new options envelope. Archive type/direction/directory validation belongs only to staff; the existing `archive:"zip"` request is unchanged and staff still strictly rejects unknown/invalid business parameters. Extras do not enter data/open or commit. This allows remote **business prepare options** to evolve within the stable contract, not arbitrary protocol/permission/bridge/data changes without a host upgrade.

All transports return the same prepared resource metadata, not a file-specific HTTP ticket. The host opens `purpose:"cc.qqxing/files",resourceId:transferId,direction:"host-to-remote"|"remote-to-host"` through the shared DataSession, also used by terminal; a live, unused resource binds once. Stdio configure explicitly requests and returns `transport:"stdio"`; open sends `{binding,channel,open}` with a host-allocated strictly increasing positive safe integer channel and returns `{}`. Remote fences the ID before asynchronous business admission. No listener, endpoint, HTTP link or ticket is created; old/new stdio data mismatch leaves only optional DATA Apps/transfers unavailable, without HTTP fallback or replay. HTTP/reverse configure `{binding,origin?}`, open `{binding,open,link?}` and temporary DataLink remain unchanged; its relative positive expiresInMs is bounded by the open timeout and measured with local monotonic time.

Direct HTTP continues to mount `/mcp/data/<binding>` on the MCP listener before JSON parsing. Only direct HTTP accepts configure origin for a configured HTTPS proxy advertisement; it grants no outbound fetch permission and does not trust Forwarded. Stdio/reverse reject origin, and HTTP rejects `transport:"stdio"` before resource allocation. Local and Docker stdio use the control pipe with no `39173` publication, application-data listener or bootstrap metadata. Docker ownership, permissions, mounts and cleanup remain unchanged. Extension preflight still requires Linux containers and verified local Unix socket/`npipe` endpoints for HTTP/stdio; HTTP retains reachable-loopback requirements. Removing the stdio port, including a `--network=none` check, is not proof that remote Docker, arbitrary Desktop, native packages or mounts work. Windows arm64/macOS are untested and musl/Alpine terminal is not promised; see [README topology limits](../README.md).

Reverse control remains SSE + POST on the existing Next Web port. Open supplies the exact current-session `/api/mcp/reverse/data/<session>` endpoint; remote resolves it against `--ru`, validates it and actively GETs/PUTs without an inbound listener. Direct HTTP returns the staff endpoint link for host access. Both retain raw binary get/put, cumulative ACK and close legs with Bearer token/X-Data-Binding checks, no browser Origin, arbitrary URL, redirects or replay. Tickets never reach the iframe. Proxy/CA-aware clients remain injected by the connection; actual proxy streaming needs validation.

Deliveries are at most 64 KiB, with a **256 KiB window per channel/direction**. Stdio uses `cc.qqxing/data/v1/frame` notifications carrying binding/channel and data/end/ack/close: canonical Base64 data has 1..65536 decoded bytes, a strict sequence and absolute byte offset; ACK has a separate cumulative sequence/offset/ended. Invalid encoding, size, direction, sequence or window usage fails the channel before payload allocation; close is abnormal, not successful EOF. Control/data share one FIFO writer with one setImmediate yield between messages and no priority. HTTP/reverse retain their raw binary/ACK wire. In both implementations, write admits only bounded chunks, waits when the window fills and rejects concurrent writes. ACK follows awaited serial receiver.data/end, not SDK write/drain or socket/fetch completion; end/closed success requires final consumption confirmation. ACK sends coalesce into one in-flight plus one latest value. File ACK is not commit. All transports retain TransferManager authorization, leases and commit checks; transfer_file retains its model name/parameters and file URI validation, relaying bounded bytes rather than whole-file buffers.

Uploads progress through prepared/streaming/ready before an explicit digest-checked commit. Downloads read a private version-checked snapshot and then release it, never commit or delete the source. Writes publish atomically through the shared file core; network I/O does not hold the global write mutex. A cancellation admitted before commit prevents publication; after commit admission it is `TOO_LATE`. `status` can return preparing, prepared, streaming, ready, complete, committing, committed, released, expired, failed, or unknown as applicable. Explicit failures include `published:false`; unknown or an unavailable record is not proof of no publication. A lost commit receipt must not trigger an automatic write retry, re-prepare or protocol fallback.

Current source removes the **100 MiB per-file hard limit** from files-v1 streaming uploads and cross-MCP transfers. File sizes must be nonnegative safe integers; there is no replacement 1 GiB/2 GiB cap. Available disk space and the existing lifecycle limits still apply. Older staff-mcp 2.0.4 peers retain their 100 MiB limit; updating only one endpoint or the host does not remove a remote peer's limit.

Read preparation copies and hashes a private source snapshot in bounded **64 KiB** blocks, never a whole-file buffer. It reads at most the initial stat size and checks source identity, size and timestamps afterward; short reads, growth or detected changes fail preparation rather than following an indefinitely growing file. Cancellation, disconnection and lease expiry interrupt preparation between bounded I/O operations. Allow disk space for the full source snapshot and the destination staging file (as well as the existing destination until atomic publication); this is streaming, not zero-copy or disk-quota management. Browser uploads pass a `File` to the host, not a whole-file `arrayBuffer`, and have no 100 MiB pre-rejection in the staff UI.

Current limits remain **two active transfers per session**, **128 operation records**, a **30-second remote monotonic lease**, and **five-minute final-state record retention**. The host renews after rechecking authorization, normally within ten seconds, and has its own five-minute idle-transfer timeout. Remote record retention is not an idle lease or persistent transaction journal; reconnect/restart invalidates old handles. Normal session close waits for pending preparation/byte I/O and any admitted commit to settle before removing private staging; it does not relabel an admitted or unknown publication as released or rolled back. The synchronous exit fallback remains registered until asynchronous staging cleanup succeeds. Process crashes can leave private staging; this is not a disk-quota or cross-restart recovery service. The common dataSession defaults to **four** active logical channels, a **15-second** open/missing-leg timeout and a **60-second** consumption-progress timeout, checked only while bytes await consumption ACK, end awaits final confirmation, a receiver callback is running, or an ACK is pending/in flight. A healthy idle PTY with no pending consumption/end work is not closed merely for having no bytes for 60 seconds; business leases and control-connection liveness still apply. These data-layer limits do not replace business leases or bound whole-process memory.

Large-file preparation still has to fit the existing **30-second prepare request timeout** and **30-second remote lease**, which starts on admission, not after snapshot completion. Removing the size cap does not extend either deadline: slow disks, hashing or large files can still time out or expire during preparation. Existing authorized renewal behavior is unchanged; there is no automatic retry, re-prepare or resume after timeout. Use the original operation status and cleanup lifecycle, and never treat an unknown or missing record as proof of non-publication.

The matching host uses native browser attachment streaming and the browser download manager for App downloads, without a 100 MiB file-size limit or whole-file Blob cache. Streaming on staff is not a direct browser-to-staff path; reverse bandwidth and latency still depend on the deployment network and consumer speed. Package/native ABI/libc compatibility is a deployment requirement, not a property of the HTML bundle. Older hosts and remote staff-mcp 2.0.4 peers can still enforce their previous limits and require coordinated upgrades.

The UI expands transfer feedback on download/upload actions. Download preparation has indeterminate progress. `downloadReceive` only acknowledges snapshot metadata: `ready` means prepared, with zero bytes received, not a cached complete file. Clicking “保存到设备” invokes the native browser GET through `downloadSave`; a `{handedOff:true,receiving:true}` acknowledgment keeps the job running and cancellable while host status polling reports actual byte progress. Late save responses cannot overwrite a newer progress/terminal/cancellation state. For older hosts without `receiving:true`, the legacy browser-handoff label is retained. `completed` means the host verified the response stream; transfer progress and browser handoff do not certify a local disk write or a local-file checksum. Manual retry prepares a new download only on explicit user action; there is no automatic replay. Saving, completion and cancellation in the native download manager remain browser-owned. Cleanup releases temporary remote snapshots through the existing files-v1 lifecycle, never deletes the source, and does not claim to undo bytes already handed to the browser.

Image preview is limited to 2 MiB. Cancellation admitted before the final commit prevents publication; once commit has started the host returns `TOO_LATE` rather than claiming an already-issued write was undone.

Terminal is a separate human app, not an implicit capability of enabling files; the host does not add a separate terminal permission switch. It requires the existing current-chat MCP grant, staff terminal extension enablement, a loadable optional `node-pty` on Linux or Windows (build >= 18309), and negotiated streams/data v1 with a usable duplex dataSession over supported local stdio/Docker, direct HTTP or reverse topology. Its starting cwd is not an OS sandbox, and it runs under the staff process's operating-system identity. Terminal I/O is not added to model context or chat history. It uses the generic browser-host `/api/mcp/app-stream` WebSocket (`chat-app-stream-v1`) with rendering-consumption ACKs, a separate 120-second browser-presence deadline and server-returned remote lease (staff defaults to 30 seconds), not the file app's two-hour TTL. Only the browser host refreshes presence every 10 seconds; the generic stream module schedules remote renewal from the returned lease; opening the app starts a PTY once, without another open button or high-risk confirmation. Exit/failure leaves the app shell available for manual reconnect, never automatic replay. Backpressured process exit can have incomplete output: current source reports remote `status.error:{code:"OUTPUT_INCOMPLETE",message:string}`, and host generic stream-frame `incomplete?:boolean` / `error?:{code:string,message:string}` on abnormal close/status, with UI warning handling. The generic `incomplete` flag belongs to the host stream result, not remote status; the app-local terminal adapter maps it to its presentation warning. These diagnostics detect possible loss; they neither recover missing bytes nor guarantee lossless output, even with exit code 0 or EOF. See the [terminal UI contract](terminal.md) and chat-ai's authoritative terminal protocol for lifecycle and limitations.

A configured optional file root that cannot initialize disables files with a stderr warning; it does not replace or widen the standard workspace tool roots. Invalid CLI syntax is still an error, and workspace/mount access errors still fail the relevant startup or file/tool operation rather than granting access. Availability and extension-version negotiation remain distinct from authorization.

## Building and shipping the UI

From a development checkout with dependencies installed:

```sh
npm run build
```

The build compiles server TypeScript, type-checks the browser UI via `tsconfig.ui.json`, and runs `scripts/build-file-manager.mjs`. esbuild bundles React, CodeMirror, application code, and CSS into the self-contained `dist/src/file-manager/ui/index.html`. No external CDN or browser network request is required to render it.

The HTML is loaded relative to the compiled extension module. The package includes `dist/src`, so it carries this generated Resource, including when staff-mcp is read-only mounted into a Docker container. `prepublishOnly` runs the build; plain server compilation or `tsx src/index.ts` alone does not create the HTML Resource at the compiled module location. Rebuild and distribute the package for UI changes instead of relying on a developer's working-directory asset.

Deploy matching host bridge and staff-mcp assets, reconnect MCP and reopen Apps after upgrading. An already-open iframe is not hot-replaced by publishing a new package.


## Host boundary and bridge v1

The descriptor advertises `bridgeVersion:1`, `scope:"workspace"` and `capabilities.files:{version:1,upload:true,download:true}`. File CRUD remains in `methods`; managed files lifecycle calls cannot bypass the files module through ordinary RPC. The iframe handshake and message envelopes retain version 1; the 2.0.0 extension contract requires matching host assets. The file UI now calls generic `readBytes` and receives only bounded `{data:base64}`; it selects raster-image MIME itself. The host does not interpret filename extensions. `maxBytes` is a client receive budget, removed before remote prepare; host inline `readBytes` remains capped at 2 MiB. Native browser attachment streaming downloads, streaming uploads and cross-MCP relays have no 100 MiB file-size hard limit in matching upgraded endpoints; this does not redefine the server's text/path limits. Deploy matching host/descriptors/UI assets and reopen existing Apps; previous byte-preview methods have no compatibility fallback.

The independent files-v1 contract adds `stat {rootId,path}->{version}` for opaque file-version lookup. It uses the same FileCore safety checks, does not prepare a snapshot or transfer, and rejects directories. Agent force-copy no longer calls the private file-manager/stat App method. Older peers without files/v1/stat fail that capability explicitly; clients must not omit expectedVersion, use a digest as a version, or replay the write. Existing non-force operations keep their request/response shape.

The transport-neutral data kernel accepts structurally valid purposes only through an explicit outer capability gate. The staff built-in runtime registers only enabled/negotiated files and terminal resources. The host admits negotiated files plus the purposes in current parsed streams-capable Apps, read lazily after discovery. Accepting new purpose syntax does not grant unknown business access.

### HTTP session lifetime

The HTTP listener has a fixed 64-session capacity and no MCP idle-expiry timer. Explicit session close, failed initialization and shutdown still wait for owned staging, in-flight I/O and admitted commits; cancellation/disconnect is not proof that a write stopped. File leases and final-record retention remain independent, without changing published/unknown outcomes. Clients should close unused MCP sessions; see the README for capacity and cleanup.

### Capability composition and streams

File UI/CRUD and file publication remain business-owned; host FilesBridge/resource modules preserve operation IDs, quotas, leases, commit/status and unknown-publication handling. Generic AppFrame/MCPAppService/ChatMCPServer do not interpret file-manager or PTY parameters. New Apps that reuse supported capabilities do not require host-core changes. New host permissions/capabilities must be explicitly registered at discovery/validation, server resource-module and browser-bridge composition roots; they cannot be granted by a descriptor alone.

A leased byte App declares `capabilities.streams:{version:1,purpose,create,renew,status,close,commands?}` and requires streams/data v1 plus chat scope. Descriptor lifecycle/command values are distinct namespaced RPC methods, excluded from ordinary `methods`. Generic create uses `{operationId,params}` and returns `{resourceId,leaseMs,metadata?}`; renew uses `{operationId,resourceId}`, status returns active/closed plus opaque metadata/error, close uses `{operationId,reason:"user"}`, and commands use `{resourceId,params}`. Host exposes only its own streamId, not remote resource IDs or raw tickets. It preserves bytes, uses raw-byte cursors and Base64 on the browser bridge (also used by the independent backend stdio framing), and waits for real consumption ACK/EOF; abnormal close retains buffered bytes and marks `incomplete`, never clean success. Terminal business conversion belongs to staff's extension/UI adapter; see [terminal](terminal.md).

Reverse transport sources can later be extracted to MCP Client (host)/Server (remote) SDKs; no package split is done now. HTTP/TLS/proxy policy in `src/reverse/http.ts`, factory/extension/data setup and reconnect in `src/transports/reverse.ts`, and host Web auth/management remain integration. Transparent transports do not intercept data RPC; reverse wire and raw HTTP stay unchanged.

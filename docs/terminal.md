# Terminal app UI

This document describes the staff-mcp 2.2.0 terminal contract. Windows native ConPTY and eligible Windows Docker Desktop Linux-container extension support are included in staff-mcp 2.0.4, not 2.0.3; the native dependency pin and APPS/FILES/STREAMS v1 are unchanged; current modern HTTP uses DATA2. Reverse and extensions require a matching chat-ai host implementing reverse v1 and session-relative data paths, with matching host/descriptors/UI assets. The authoritative generic stream contract is `chat-ai/docs/protocol/streams.md` at that compatible host version; `chat-ai/docs/protocol/terminal.md` defines only the PTY business adapter, safety boundaries and UI differences. No Chat8/schema9/format7/share protocol2 data migration is required. See [compatibility and upgrade](../README.md#compatibility-and-coordinated-upgrades).

staff-mcp 2.2.0 (2026-11-08) uses split MCP SDK 2 (`client`/`server`/`core` 2.4.0, `node` 2.1.2), accepts legacy/modern `2026-07-28` clients, and adds DATA2 business ownership on modern HTTP. Pair with chat-ai `tmp/inner-mcp-stdio` commit `1d659874f4da0540274ea454f016cebaa6838945` or a compatible successor, including matching host/descriptors/UI assets and the public `chat-ai/docs/protocol/data-binding.md` contract. Standard Skills and their legacy tool compatibility markers add no terminal grant or execution approval. HTTP/reverse raw channel wire and consumption ACKs remain unchanged, with no automatic fallback or input replay. The release target is Linux x64, not new Windows/macOS/musl validation, company-network acceptance or full end-to-end verification; the corporate reverse I/O issue is not claimed fixed.

The no-port stdio data, shared Bash initialization and terminal close-button simplification introduced in 2.0.7 are retained, as are the container/resource changes from 2.1.0. The historical 2.0.7 host pairing was chat-ai commit `5bfa6a4321d258e5129b250da248adff96b6ad42` or a compatible descendant for its protocol and permissions; use the newer pairing above for 2.2.0. Installing this npm package alone does not update the host's bundled staff dependency or deploy/restart its endpoints, and does not provide host Docker template/user-script orchestration. Older stdio hosts may lack optional data-dependent Apps/transfers while healthy standard MCP remains usable.

Requires Node.js 22.22.2 or newer on the host and in Docker. Current source supports Linux PTY and Windows native ConPTY; Windows build >= 18309 is necessary but does not guarantee native loading or shell availability. The Docker wrapper does not query engine OS; container startup and these in-container checks decide availability. HTTP/stdio still require a verified local Unix socket or named pipe (`npipe`) endpoint. The wrapper retains POSIX container paths and is not newly adapted to Windows containers. Windows arm64 and macOS remain untested on real hardware; musl/Alpine terminal support is not promised. Optional discovery/data negotiation failures still preserve an otherwise healthy standard MCP connection; explicit terminal platform/native/shell startup errors do not degrade silently. The old reverse handshake itself is incompatible even with extensions disabled: upgrade both endpoints rather than relying on extension degradation. There is no old-protocol fallback or automatic terminal input replay.

`terminal` is an independent, human-operated app enabled with `--extensions terminal` or `--extensions files,terminal`. It requires Linux or Windows (build >= 18309), a loadable optional `node-pty`, an executable shell, and streams v1 with a usable duplex dataSession. DATA is v1 on stdio/reverse in either MCP era and on legacy HTTP, but v2 on modern HTTP; APPS/FILES/STREAMS and the browser bridge remain v1. All extensions are disabled by default; apps/data dependencies and terminal's streams v1 manifest are derived automatically. When platform/native PTY/shell prerequisites are unavailable, an explicit terminal request fails startup with an error, even when files is also requested; the default disabled state does not load native PTY code. An unverified/nonlocal HTTP/stdio daemon endpoint likewise fails explicit terminal requests rather than silently dropping them; files-only retains its endpoint-check degradation. There is no outer engine OS precheck for either extension; native platform/ABI and shell checks inside the running process remain. Container launch failure remains a startup failure, not optional-extension degradation.

Stdio now carries bounded Base64 frames on the control pipe, with no data listener, endpoint, HTTP ticket, `39173` publication or bootstrap metadata. Each frame is at most 64 KiB decoded; each channel/direction has a 256 KiB consumption window and control/data share a FIFO writer without priority. Configure explicitly requests and returns `transport:"stdio"`; mismatch disables optional DATA Apps, not healthy standard MCP, without HTTP fallback or replay. HTTP/reverse keep raw HTTP on the existing ports; HTTP still requires a local daemon and reachable loopback, and reverse retains valid-mount and actual runtime prerequisites without a separate daemon OS check. Removing stdio network dependence does not expand remote Docker or platform support.

The host uses the existing current-chat MCP grant and same-origin browser requests, without a separate terminal permission switch or high-risk confirmation. HTTP/HTTPS follows the site-wide deployment policy, with no terminal-only TLS gate or origin allowlist. HTTPS is recommended for the whole site; HTTP does not encrypt login sessions, tool calls or terminal traffic. Reverse resolves the host-provided current-session data path against the existing `--ru` origin; chat-ai does not need a public URL setting. Upgrade both endpoints together; reverse and legacy HTTP keep DATA1, while modern HTTP uses the public DATA2 control capability. Raw channel framing/ACKs are unchanged; stdio explicitly negotiates its frame transport. Topology and CLI details are in the [README](../README.md). The self-contained HTML Resource is built to `dist/src/terminal/ui/index.html`; terminal bytes do not add model tools, chat messages or chat history.

## Native dependency delivery

The optional dependency remains pinned exactly to the official prerelease `node-pty@1.2.0-beta.18`, including Linux x64/arm64 N-API prebuilds for glibc >= 2.28 and Windows x64/arm64 ConPTY prebuilds. A shipped architecture build is not hardware validation: Windows arm64 and macOS are untested. Windows requires build >= 18309, compatible native binaries and system dependencies; there is no winpty fallback. Linux still requires system libraries such as `libstdc++` and `libgcc`; both platforms require an executable shell. No user image is upgraded automatically; musl/Alpine terminal support is not promised (Alpine examples without terminal remain standard MCP examples).

Docker still mounts the host package and `node_modules` read-only. This fixes prebuilt delivery for normal installs, not complete container dependency isolation: local build leftovers and architecture/platform/libc mismatches remain limitations. N-API does not remove system-library or platform requirements.

## Long HTTP streams and failure boundaries

The unreleased paired host/endpoint supports opt-in reuse of a live shell while the staff factory remains alive. Network retirement ends the attachment, not necessarily the shell. The HTTP stability policy below remains unchanged. This is not output-history storage, screen restoration, old-stream resumption, input replay, or recovery across staff/container/host restart.

Raw HTTP data GET/PUT use a data-only request policy: no finite response-header/body-idle timer for an established leased stream. GET headers can legitimately be delayed until first output; PUT responds at EOF. PUT fetch itself starts only when the first actual byte or EOF is queued, avoiding an idle header-less TCP connection; ready reserves the one-shot leg, including empty uploads. The independent ready/open deadline, pending-consumption timeout, resource lease and control lifecycle remain. Control requests and finite ACK/ready/close requests retain normal HTTP defaults, with the same owned pool, TLS/proxy/redirect restrictions.

The direct HTTP listener retains native header limits and a bounded ordinary request-body deadline. Only after the data session validates the original token/binding/ticket, claims the one-shot PUT leg and accepts its encoding does it release that request's body deadline. A matching chat-ai host installs the equivalent early HTTP policy for reverse uploads. No arbitrary URL/header disables request protection, and no keepalive characters are added to terminal bytes. External proxies may impose their own limits and require separate deployment verification.

Modern `server/discover` and legacy `ping` responses have a strictly validated, bounded liveness lane, independent of ordinary reverse POSTs. Read-only probes are not blocked by subscription filesystem preflight. Only SDK-generated subscription acknowledgements associated with a forwarded listen generation release the SDK ingress after synchronous bounded enqueue; physical ACK/notification FIFO order is unchanged, failed sends close that connection, and shutdown awaits the tracked sends. This is not a delivery acknowledgement. This does not make all RPCs concurrent, extend authorization, or retry unknown operations. Errors distinguish a stopped stream that can be manually recreated from an invalid App that must be reopened from its workspace; late successful stream-open handles are cleaned on their original bridge rather than silently leaked.

## Opening and stopping

Without shell initialization configured, on Linux a valid absolute executable `$SHELL` is selected automatically, otherwise `/bin/bash`. It starts with `-i`; normal profiles/startup files and HOME behavior are unchanged, with no further shell fallback if unavailable. On Windows, executable `pwsh.exe` is preferred, then `powershell.exe` (including the system installation), using `-NoLogo -NoProfile`; fallback is `ComSpec`/system `cmd.exe` with `/d` to disable CMD AutoRun. Candidates must pass an executable check; Windows does not use `$SHELL` to select the shell. Missing shell or node-pty fails explicit terminal startup. There is no public shell-selection parameter: `--shell` is removed and fails as an unknown option. PATH, virtual environments and other staff environment variables are preserved. [`src/terminal/pty.ts`](../src/terminal/pty.ts) filters only these exact internal control keys: `STAFF_GLOBAL_DIR`, `STAFF_MCP_IS_DOCKER`, `MCP_REVERSE_URL`, `MCP_REVERSE_TOKEN`, `MCP_REVERSE_NAME`, `MCP_HTTP_TOKEN`, `STAFF_MCP_HTTP_TOKEN`, `STAFF_MCP_REVERSE_TOKEN`. Missing `TERM` becomes `xterm-256color`, and `SHELL` is set to the selected executable. This is not a general secret scrubber or environment sandbox; the same OS identity may still access credentials and other files.

Selecting the Shell App automatically starts one PTY after the host bridge becomes usable and the visible xterm viewport has been measured with its fonts ready; there is no additional open button or high-risk confirmation. The initial PTY uses those fitted columns and rows rather than starting at 80×24 and resizing after the first prompt. Hidden, zero-sized or not-yet-measurable views wait for a usable layout. The toolbar reserves its control height before connecting, so showing the buttons does not invalidate the initial row measurement; subsequent viewport changes continue through the normal resize path. The toolbar shows the returned shell and starting path. The PTY defaults to staff's workspace `main`, independently of file-app roots, and inherits staff's environment and OS identity, not a separate browser-user identity; its cwd is not an operating-system sandbox. Without shell initialization configured, Linux startup profiles remain normal; Windows PowerShell profile loading/CMD AutoRun are disabled as above. This is not a guarantee that shell, programs or the OS never record history, even though chat-ai does not add terminal bytes to chat history.

**清屏** clears only local display and scrollback and sends no shell command. Closing the App/page releases its attachment; **结束会话** is a separate, explicitly confirmed command that ends the current shell. Confirmation stays inside the iframe and does not require modal/sandbox permissions. Failed or uncertain termination is not automatically replayed. Normal staff service shutdown waits for all attached/detached PTYs; a single Reverse reconnect or DATA2 owner retirement does not shut down the factory's retained sessions. Linux retains TERM-to-KILL escalation and Windows closes its owned ConPTY console, both best effort. Neither guarantees removal of every detached descendant nor rolls back filesystem/network effects.

Hiding the browser page or switching/collapsing app views within the same chat keeps the current App/attachment, including read/ACK; visibility gates new opening/input/resize. Page exit, App close and network loss fence the old attachment and discard unsent input. Reopen or **重新连接** tries a new authorized attachment to the original shell; a live writer in another page (or an old connection not yet expired) returns a conflict instead of being stolen. A retired MCP generation still requires reopening the App from its workspace. Temporary catalog/settings errors are not confirmed revocation. Late open/channel results are cleaned only on their original attachment, and a newly spawned shell never bound to data is not left retained after cancellation.

## Live shell reuse, not history storage

The terminal descriptor explicitly opts into `streams.reuse:true`. A paired host injects a private 64-hex `reuseKey` outside UI business params, scoped to the authorized user, chat/settings context, stable MCP target/source and App. It never exposes this capability to the iframe, logs, model or browser storage. Current DATA authorization is required independently; knowing a public terminal/operation ID is insufficient. No key means the previous connection-owned lifetime. Older strict hosts require a coordinated upgrade for the new descriptor.

A factory-scoped store holds each PTY while connection/DATA2 objects hold disposable attachments. A live original shell is reused only when no writer is attached; different root parameters are rejected. Each attachment has a new operation/resource/channel and raw-byte cursor, and old input/pump/close completions cannot control its successor. Pending input is fenced and settled before another attachment can write; already written bytes cannot be undone and are never replayed.

Detached shells are retained for at most **two hours** from detachment, using a monotonic deadline that output does not renew. At most **32 starting/running/closing PTYs per factory**, including detached shells, are allowed; a full pool rejects creation rather than evicting another shell. Per DATA1 session/DATA2 owner limits remain two active attachments, 128 operation records and five-minute terminal receipt retention. Explicit termination, shell exit, retention expiry or true staff service shutdown ends the shell. No registry, shell identity or output is persisted, and process/container restart recovery is not promised.

On detach the old bounded transmission queue is discarded. Staff keeps reading and discards offline output so an unattended program is not indefinitely blocked by a paused output pipe. It does not archive history or claim browser consumption ACKs for discarded bytes. Reattachment resets the local terminal parser/screen and reports **已接回原终端**; if the original shell no longer exists, it reports a newly created terminal instead. Shell-maintained command history, current directory, variables and programs survive only because the original shell survives. Offline screen/scrollback and full-screen application restoration are not promised. A prompt may need a user-entered Return; the UI never injects Return, Ctrl-L or another synthetic command.

Authorization is rechecked before every new attachment and interaction. Confirmed active revocation requests termination where reachable, but a detached/unreachable process may remain until its retention deadline. There is no new host-side background process inventory or authorization polling service, no promise to reverse previously started program side effects, and no cross-chat/user/source transfer. A host runtime restart also loses its private reuse identity; an unreachable old shell remains bounded by remote retention.

## Shared shell initialization

`STAFF_MCP_SHELL_INIT` is an optional deployment environment variable containing an absolute readable script path within the staff environment, not a tool/terminal parameter. Configuration requires Linux and executable `/bin/bash`; missing Bash, an invalid path or failed source never falls back to `sh`. The management Node process validates the path but never reads/parses the script contents or sources it itself.

Each `execute_command` uses `bash -O expand_aliases -c` with a fixed source-then-eval wrapper and positional path/command arguments. Only the original, already executable user command is evaluated after successful source. Each new PTY uses `/bin/bash --rcfile <private-bootstrap> -i`; the owned temporary bootstrap contains only a fixed source/failure guard, not the user's script, and is removed on spawn failure or PTY exit. Nonzero source exits instead of presenting a prompt. With initialization enabled, the normal user Bash rc file is replaced, `BASH_ENV` is removed from the child environment, and `STAFF_MCP_SHELL_INIT` is retained for descendants; existing control-key filtering remains in effect.

Aliases, functions, exports and directory changes are available in the same shell. Initialization stdout goes to stderr (PTY output stays in the terminal data stream), never management/MCP stdout. Source stderr is suppressed to avoid Bash diagnostics quoting secret-bearing script lines; ordinary nonzero source returns report only a fixed message. Scripts may enable `set -e`, which remains effective and can terminate the shell before that message; staff does not enable it implicitly. Intentional script stdout is still visible, so scripts must not print secrets. Initialization runs repeatedly, not as a one-time install, with existing staff OS permissions and no new sandbox. Changes apply only to subsequent commands/new PTYs, never to already running shells. Background task IDs, cancellation, process-group stop, PTY leases and native cleanup are unchanged; failure/cancellation never automatically replays input. An absent/empty variable preserves all previous behavior, including Windows. This does not make aliases available to arbitrary third-party processes.

## Host bridge contract

The app uses the shared Apps bridge. It announces `mcp-app-ready` and accepts the parent `mcp-app-connect` v1 handshake with nonce, instance ID, and one MessagePort. Theme snapshots and `{type:'lifecycle', enabled, connected, visible, message?}` use that authenticated port. No browser-direct network, CDN, clipboard API, web-link addon, iframe sandbox relaxation, or extra permission is required. OSC 52 clipboard sequences and OSC 8 hyperlinks are consumed without clipboard access or link activation.

The terminal descriptor uses `capabilities.streams:{version:1,purpose:"cc.qqxing/terminal",create:"cc.qqxing/terminal/v1/create",renew:"cc.qqxing/terminal/v1/renew",status:"cc.qqxing/terminal/v1/status",close:"cc.qqxing/terminal/v1/close",reuse:true,commands:{resize:"cc.qqxing/terminal/v1/resize",terminate:"cc.qqxing/terminal/v1/terminate"}}`, `scope:"chat"`, `methods:[]` and required streams v1 plus DATA2 on modern HTTP (DATA1 elsewhere). The manifest advertises streams, not terminal; terminal remains the business RPC namespace and data purpose. Lifecycle and command methods must not be ordinary App RPCs.

The shared streamOpen/write/command/read/close envelopes, `/api/mcp/app-stream` WS (`chat-app-stream-v1`), cursor/ACK/EOF/final-flush rules, budgets, ownership, presence/leases and single-runtime deployment limits are defined once in `chat-ai/docs/protocol/streams.md`, not by this terminal app.

The app-local [`stream-adapter.ts`](../src/terminal/ui/stream-adapter.ts) passes `{rootId?,cols,rows}` to streamOpen and maps resize to streamCommand. It encodes UTF-8 input as Base64, decodes output Base64 to Uint8Array and feeds xterm; only after xterm's write callback does it read-next/ACK. It interprets metadata.path/shell/exitCode; the generic host does not interpret PTY fields or decode UTF-8. On STREAM_DRAINING the UI disables new interaction/discards unsent input but continues read/ACK to the final frame.

node-pty can lose tail output when exit races paused reads. Staff reports detected risk as `error:{code:"OUTPUT_INCOMPLETE",message}`. The UI adapter maps generic ended to its local exited state, metadata.exitCode to the exit display and incomplete to **输出可能不完整**; read rejection displays **输出完整性无法确认**. The warning persists through later lifecycle changes, including exit code 0, and preserves displayed content. These local names are not bridge fields; diagnostics cannot recover lost bytes or guarantee completeness, and absent warnings/EOF/exit 0 do not prove complete history.

Input requests are sequential and small inputs are coalesced within bounded pending storage, each request at most 32 KiB UTF-8 with code-point-safe splitting. Pending UI input including the in-flight request is bounded at 256 KiB; a new paste that would exceed this budget is rejected atomically before admission, without terminating the existing PTY or discarding previously admitted input. Unknown results are still never replayed. Backend deliveries can be 64 KiB; staff splits them into ordered, awaited input writes of at most 32 KiB. Linux retains raw-byte fd writes with EAGAIN handling, without UTF-8 decoding. Windows targets the ConPTY UTF-8 input pipe with one bounded write in flight; input ACK follows the pipe write callback, not mere JavaScript enqueue or locally retained bytes. DataSession preserves raw-byte semantics, host cursors/ACKs count raw bytes and the generic host does not decode UTF-8. Linux input ACK follows complete fd writes; output ACK follows xterm parser/buffer consumption (its write callback), not requestAnimationFrame/visible painting or fetch/socket enqueue. The common 256 KiB sliding ACK window permits multiple backend blocks in flight, not per-block stop-and-wait; final EOF awaits receiver.end and its ACK, while interruption fails visibly and releases blocked work. Input acknowledgement does not prove command execution.

Presence and lease scheduling still govern each attachment: staff's 30-second default attachment lease is separate from the 90-second modern HTTP DATA2 lease. Expiry fences the old handles and data connection, not a reusable shell's independent retention. Existing consumption/lease deadlines remain active; no ACK or browser presence is fabricated to retain a shell. PTY exit/draining remains distinct from authorization loss, and UI keeps read/ACK until the final frame.

ResizeObserver fits the local xterm viewport; remote resizes are debounced and ordered. Local display scrollback retains 2000 lines and is not a complete audit log. Terminal output is rendered by xterm, not inserted as HTML. Accessibility mode and the host light/dark semantic palette are enabled.

## Building

With the project's `@xterm/xterm` and `@xterm/addon-fit` dependencies installed:

```sh
npx tsc --project tsconfig.ui.json
node scripts/build-file-manager.mjs
```

The script retains the file-manager build and additionally emits the terminal Resource. It rejects terminal HTML larger than **4 MiB** and embeds both xterm packages' complete LICENSE notices, including dependency copyright, inside the HTML. It does not require external assets at runtime.

For a terminal-only UI check without compiling the server, use `node scripts/build-file-manager.mjs --app terminal --outdir /path/to/scratch`. The output is `/path/to/scratch/terminal/ui/index.html`. App registration, extension negotiation, native PTY packaging, host authorization, and browser/remote lifecycle testing are separate integration responsibilities; a successful UI bundle alone does not verify them.


## Host adapter boundary

The terminal descriptor uses `bridgeVersion:1`, generic `scope:"chat"` and streams capability; nonterminal leased-byte Apps reuse the same host modules. All iframe handshake/message envelopes retain version 1; the 2.0.0 extension contract requires matching host assets and offers no legacy compatibility path. PTY state, actual lease and process cleanup remain server-owned. The host generic stream module follows each returned positive leaseMs rather than requiring a 30-second maximum; staff retains its own 30-second default. Host browser presence and render-buffer budgets remain independent and do not extend the server's resource without a real renew request. The bridge boundary does not change the 2.0.0 reverse/raw data framing; it does not provide compatibility with pre-2.0.0 reverse handshakes.

### HTTP session lifetime

Legacy HTTP retains MCP sessions without idle expiry. Modern HTTP has no `Mcp-Session-Id` and invokes the server factory for each request; its Files/PTY/data owner outlives those request facades. The public DATA2 `control:{binding,token}` has a separately renewed 90-second lease; proofs stay in host memory, never in the UI/model. Browser presence, PTY leases, raw bytes and ACKs do not renew that binding. Ordinary tools retain their shared process state and original permissions.

Close and DATA2 expiry fence new business work, await admitted CRUD, file preparation/I/O/commit and attachment cleanup; failure does not report closed. Reusable PTYs are retained by the factory, not by the retired owner. Listener shutdown additionally ends and awaits every factory-owned PTY. Original DATA2 proof remains limited to original status/cleanup within bounded retention; it cannot access a new attachment. The combined listener cap of 64 legacy sessions plus active/closing modern bindings and 128 total proof records is unchanged. New DATA authorization plus the independent private reuse key is required to reattach; no binding control or unknown input is replayed.

### Business adapter and SDK boundary

`src/terminal/extension.ts` interprets create `{operationId,reuseKey?,params:{rootId?,cols,rows}}`, returning a fresh `{resourceId,leaseMs,metadata:{rootId,path,shell,resumed,retainedForMs}}`. Renew/status/resize retain their envelopes; close accepts `{operationId,reason:"user",retain?}`, defaulting to termination when retain is absent/false. The new `terminate` command takes `{resourceId,params:{}}` and only ends the current attachment's shell. Modern HTTP still validates and strips DATA2 control before strict business validation. Dimensions remain integer 2..1000. TerminalSession owns only this DATA1 connection/DATA2 owner's operation receipts and attachments; the factory owns reusable PTYs. The host remains generic and does not interpret shell fields.

Host stream ownership, two per-owner slots including creation, single reader, authorization, presence/lease deadlines and late-create cleanup are generic. New Apps reuse those supported capabilities without host-core business branches. New host permissions/capabilities require explicit composition-root registration, validation and authorization; descriptors alone cannot grant them.

Both reverse transport modules can later join MCP Client (host)/Server (remote) SDKs, but no SDK split is done now. They only depend on SDK/standard libraries and injected transport parameters. `src/reverse/http.ts` HTTP/TLS/proxy policy, `src/transports/reverse.ts` factory/extension/data setup and reconnect, and host auth/management remain integration; no data-protocol interception is hidden in transport.

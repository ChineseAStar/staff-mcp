# Terminal app UI

This document describes the current terminal source contract. Windows native ConPTY and eligible Windows Docker Desktop Linux-container extension support are included in staff-mcp 2.0.4, not 2.0.3; the dependency pin and extension protocol versions are unchanged. Reverse and extensions require a matching chat-ai host implementing reverse v1 and session-relative data paths, with matching host/descriptors/UI assets. The authoritative generic stream contract is `chat-ai/docs/protocol/streams.md` at that compatible host version; `chat-ai/docs/protocol/terminal.md` defines only the PTY business adapter, safety boundaries and UI differences. No Chat8/schema9/format7/share protocol2 data migration is required. See [compatibility and upgrade](../README.md#compatibility-and-coordinated-upgrades).

Requires Node.js 22.22.2 or newer on the host and in Docker. Current source supports Linux PTY and Windows native ConPTY; Windows build >= 18309 is necessary but does not guarantee native loading or shell availability. Docker preflight checks the Linux-container daemon OS, not the launcher OS; HTTP/stdio also require a verified local Unix socket or named pipe (`npipe`) endpoint, allowing eligible Windows Docker Desktop Linux containers. Windows arm64 and macOS remain untested on real hardware; musl/Alpine terminal support is not promised. Optional discovery/data negotiation failures still preserve an otherwise healthy standard MCP connection; explicit terminal platform/native/shell startup errors do not degrade silently. The old reverse handshake itself is incompatible even with extensions disabled: upgrade both endpoints rather than relying on extension degradation. There is no old-protocol fallback or automatic terminal input replay.

`terminal` is an independent, human-operated app enabled with `--extensions terminal` or `--extensions files,terminal`. It requires Linux or Windows (build >= 18309), a loadable optional `node-pty`, an executable shell, and streams/data v1 with a usable duplex dataSession. All extensions are disabled by default; apps/data dependencies and terminal's streams v1 manifest are derived automatically. When platform/native PTY/shell prerequisites are unavailable, an explicit terminal request fails startup with an error, even when files is also requested; the default disabled state does not load native PTY code. A non-Linux container daemon, unverified/nonlocal HTTP/stdio daemon endpoint or unsupported stdio Docker data topology likewise fails explicit terminal requests rather than silently dropping them. Files-only degradation is unchanged. HTTP/reverse avoid the extra stdio data-port mapping. HTTP retains local-daemon/reachable-loopback checks; reverse still requires Linux containers and valid existing mounts. Local stdio/Docker, direct HTTP and reverse share that public raw HTTP data protocol; standard MCP control transports remain unchanged. The host uses the existing current-chat MCP grant and same-origin browser requests, without a separate terminal permission switch or high-risk confirmation. HTTP/HTTPS follows the site-wide deployment policy, with no terminal-only TLS gate or origin allowlist. HTTPS is recommended for the whole site; HTTP does not encrypt login sessions, tool calls or terminal traffic. Reverse resolves the host-provided current-session data path against the existing `--ru` origin; chat-ai does not need a public URL setting. Upgrade both endpoints together; HTTP/stdio addresses and extension versions remain unchanged. Topology and CLI details are in the [README](../README.md). The self-contained HTML Resource is built to `dist/src/terminal/ui/index.html`; terminal bytes do not add model tools, chat messages or chat history.

## Native dependency delivery

The optional dependency remains pinned exactly to the official prerelease `node-pty@1.2.0-beta.18`, including Linux x64/arm64 N-API prebuilds for glibc >= 2.28 and Windows x64/arm64 ConPTY prebuilds. A shipped architecture build is not hardware validation: Windows arm64 and macOS are untested. Windows requires build >= 18309, compatible native binaries and system dependencies; there is no winpty fallback. Linux still requires system libraries such as `libstdc++` and `libgcc`; both platforms require an executable shell. No user image is upgraded automatically; musl/Alpine terminal support is not promised (Alpine examples without terminal remain standard MCP examples).

Docker still mounts the host package and `node_modules` read-only. This fixes prebuilt delivery for normal installs, not complete container dependency isolation: local build leftovers and architecture/platform/libc mismatches remain limitations. N-API does not remove system-library or platform requirements.

## Opening and stopping

On Linux, a valid absolute executable `$SHELL` is selected automatically, otherwise `/bin/bash`. It starts with `-i`; normal profiles/startup files and HOME behavior are unchanged, with no further shell fallback if unavailable. On Windows, executable `pwsh.exe` is preferred, then `powershell.exe` (including the system installation), using `-NoLogo -NoProfile`; fallback is `ComSpec`/system `cmd.exe` with `/d` to disable CMD AutoRun. Candidates must pass an executable check; Windows does not use `$SHELL` to select the shell. Missing shell or node-pty fails explicit terminal startup. There is no public shell-selection parameter: `--shell` is removed and fails as an unknown option. PATH, virtual environments and other staff environment variables are preserved. [`src/terminal/pty.ts`](../src/terminal/pty.ts) filters only these exact internal control keys: `STAFF_GLOBAL_DIR`, `STAFF_MCP_IS_DOCKER`, `STAFF_MCP_DATA_BOOTSTRAP`, `STAFF_MCP_DATA_HOST`, `STAFF_MCP_DATA_PORT`, `MCP_REVERSE_URL`, `MCP_REVERSE_TOKEN`, `MCP_REVERSE_NAME`, `MCP_HTTP_TOKEN`, `STAFF_MCP_HTTP_TOKEN`, `STAFF_MCP_REVERSE_TOKEN`. Missing `TERM` becomes `xterm-256color`, and `SHELL` is set to the selected executable. This is not a general secret scrubber or environment sandbox; the same OS identity may still access credentials and other files.

Selecting the Shell App automatically starts one PTY after the host bridge becomes usable and the visible xterm viewport has been measured with its fonts ready; there is no additional open button or high-risk confirmation. The initial PTY uses those fitted columns and rows rather than starting at 80×24 and resizing after the first prompt. Hidden, zero-sized or not-yet-measurable views wait for a usable layout. The toolbar reserves its control height before connecting, so showing the buttons does not invalidate the initial row measurement; subsequent viewport changes continue through the normal resize path. The toolbar shows the returned shell and starting path. The PTY defaults to staff's workspace `main`, independently of file-app roots, and inherits staff's environment and OS identity, not a separate browser-user identity; its cwd is not an operating-system sandbox. Linux startup profiles remain normal; Windows PowerShell profile loading/CMD AutoRun are disabled as above. This is not a guarantee that shell, programs or the OS never record history, even though chat-ai does not add terminal bytes to chat history.

**清屏** clears only the local terminal display and scrollback; it sends no shell command. Closing the terminal disables input immediately and requests remote cleanup. Closing cannot undo filesystem/network effects and does not guarantee every descendant process has ended. Normal server/session shutdown waits for owned PTY cleanup before CLI exit. Linux retains TERM-to-KILL escalation; Windows closes the owned ConPTY console on a best-effort basis, without promising cleanup of every detached descendant. Neither rolls back filesystem/network effects. This does not change normal output/ACK draining or promise cleanup after forced process termination. Input, including Ctrl-C and pasted text, goes to the PTY in order; uncertain acknowledgements are never replayed. Normal exit or PTY failure stops the current PTY but preserves the app shell for manual reconnect, not automatic restart.

Hiding the browser page or switching/collapsing app views within the same chat keeps the existing App and PTY. Visibility gates new opening, input and resize requests, not instance identity: already-admitted input, output reads and xterm consumption acknowledgements continue. Returning fits the viewport and enables input on that same PTY, without opening another shell. Genuine host lifecycle/permission loss, chat changes, explicit close, non-BFCache page exit and unmount still fence the instance, discard unsent input and request best-effort cleanup. An actually stopped or failed PTY requires manual reconnect; visibility restoration does not recreate it. Temporary settings loading or catalog-request errors are not confirmed revocation/disconnection. Real lease expiry, grant revocation or connection retirement still fences the PTY. Failed cleanup relies on host cleanup and the remote lease; a disconnected page cannot guarantee that its close request arrived. A pending open may return its terminal ID after the local instance was invalidated, so the host must fence and clean late creation results.

## Host bridge contract

The app uses the shared Apps bridge. It announces `mcp-app-ready` and accepts the parent `mcp-app-connect` v1 handshake with nonce, instance ID, and one MessagePort. Theme snapshots and `{type:'lifecycle', enabled, connected, visible, message?}` use that authenticated port. No browser-direct network, CDN, clipboard API, web-link addon, iframe sandbox relaxation, or extra permission is required. OSC 52 clipboard sequences and OSC 8 hyperlinks are consumed without clipboard access or link activation.

The terminal descriptor uses `capabilities.streams:{version:1,purpose:"cc.qqxing/terminal",create:"cc.qqxing/terminal/v1/create",renew:"cc.qqxing/terminal/v1/renew",status:"cc.qqxing/terminal/v1/status",close:"cc.qqxing/terminal/v1/close",commands:{resize:"cc.qqxing/terminal/v1/resize"}}`, `scope:"chat"`, `methods:[]` and required streams/data v1. The manifest advertises streams, not terminal; terminal remains the business RPC namespace and data purpose. Lifecycle and command methods must not be ordinary App RPCs.

The shared streamOpen/write/command/read/close envelopes, `/api/mcp/app-stream` WS (`chat-app-stream-v1`), cursor/ACK/EOF/final-flush rules, budgets, ownership, presence/leases and single-runtime deployment limits are defined once in `chat-ai/docs/protocol/streams.md`, not by this terminal app.

The app-local [`stream-adapter.ts`](../src/terminal/ui/stream-adapter.ts) passes `{rootId?,cols,rows}` to streamOpen and maps resize to streamCommand. It encodes UTF-8 input as Base64, decodes output Base64 to Uint8Array and feeds xterm; only after xterm's write callback does it read-next/ACK. It interprets metadata.path/shell/exitCode; the generic host does not interpret PTY fields or decode UTF-8. On STREAM_DRAINING the UI disables new interaction/discards unsent input but continues read/ACK to the final frame.

node-pty can lose tail output when exit races paused reads. Staff reports detected risk as `error:{code:"OUTPUT_INCOMPLETE",message}`. The UI adapter maps generic ended to its local exited state, metadata.exitCode to the exit display and incomplete to **输出可能不完整**; read rejection displays **输出完整性无法确认**. The warning persists through later lifecycle changes, including exit code 0, and preserves displayed content. These local names are not bridge fields; diagnostics cannot recover lost bytes or guarantee completeness, and absent warnings/EOF/exit 0 do not prove complete history.

Input requests are sequential and small inputs are coalesced within bounded pending storage, each request at most 32 KiB UTF-8 with code-point-safe splitting. Pending UI input including the in-flight request is bounded at 256 KiB; overflow stops the instance instead of silently dropping/replaying input. Backend deliveries can be 64 KiB; staff splits them into ordered, awaited input writes of at most 32 KiB. Linux retains raw-byte fd writes with EAGAIN handling, without UTF-8 decoding. Windows targets the ConPTY UTF-8 input pipe with one bounded write in flight; input ACK follows the pipe write callback, not mere JavaScript enqueue or locally retained bytes. Data v1 stays raw binary, host cursors/ACKs count raw bytes and the generic host does not decode UTF-8. Linux input ACK follows complete fd writes; output ACK follows actual xterm rendering, never fetch/socket enqueue. The common 256 KiB sliding ACK window permits multiple backend blocks in flight, not per-block stop-and-wait; final EOF awaits receiver.end and its ACK, while interruption fails visibly and releases blocked work. Input acknowledgement does not prove command execution.

Presence and lease scheduling belong to the generic host stream contract, not an iframe timer. Staff retains its 30-second default remote lease. Hidden views keep output consumption active; BFCache/freeze does not guarantee indefinite PTY survival after presence or pending-consumption deadlines expire. PTY exit/draining is distinct from revocation or expiry; the UI retains read/ACK until the final frame rather than treating normal exit as loss of authorization.

ResizeObserver fits the local xterm viewport; remote resizes are debounced and ordered. Local display scrollback retains 2000 lines and is not a complete audit log. Terminal output is rendered by xterm, not inserted as HTML. Accessibility mode and the host light/dark semantic palette are enabled.

## Building

With the project's `@xterm/xterm` and `@xterm/addon-fit` dependencies installed:

```sh
npx tsc --project tsconfig.ui.json
node scripts/build-file-manager.mjs
```

The script retains the file-manager build and additionally emits the terminal Resource. It rejects terminal HTML larger than **4 MiB** and embeds both xterm packages' complete LICENSE notices, including dependency copyright, inside the HTML. It does not require external assets at runtime.

For a terminal-only UI check without compiling the server, use `node scripts/build-file-manager.mjs --app terminal --outdir /path/to/scratch`. The output is `/path/to/scratch/terminal/ui/index.html`. App registration, extension negotiation, native PTY packaging, host authorization, and browser/remote lifecycle testing are separate integration responsibilities; a successful UI bundle alone does not verify them.


## Host adapter boundary

The terminal descriptor uses `bridgeVersion:1`, generic `scope:"chat"` and streams capability; nonterminal leased-byte Apps reuse the same host modules. All iframe handshake/message envelopes retain version 1; the 2.0.0 extension contract requires matching host assets and offers no legacy compatibility path. PTY state, actual lease and process cleanup remain server-owned. The host generic stream module follows each returned positive leaseMs rather than requiring a 30-second maximum; staff retains its own 30-second default. Host browser presence and render-buffer budgets remain independent and do not extend the server's resource without a real renew request. The bridge boundary does not change the 2.0.0 reverse/raw data framing; it does not provide compatibility with pre-2.0.0 reverse handshakes.

### HTTP session lifetime

HTTP MCP sessions have a fixed 64-session capacity and no idle-expiry timer. Existing terminal leases, browser presence, data-consumption deadlines and PTY output/exit cleanup remain unchanged; they do not renew or expire the MCP session itself. Explicit session close and listener shutdown still wait for owned PTY cleanup. Clients should explicitly close unused MCP sessions; see the README for capacity and cleanup.

### Business adapter and SDK boundary

`src/terminal/extension.ts` interprets the generic envelopes: create `{operationId,params:{rootId?,cols,rows}}` returns `{resourceId,leaseMs,metadata:{rootId,path,shell}}`; renew `{operationId,resourceId}` verifies the binding and returns `{resourceId,leaseMs}`; status `{operationId}` maps actual PTY state to active/closed and closed exit code to metadata; close `{operationId,reason:"user"}` returns an opaque object; resize uses `{resourceId,params:{cols,rows}}`. Dimension validation remains 2..1000 in staff, as do PTY state/cleanup and quotas (two active PTYs/session, 128 operation records, five-minute final-record retention). Internal TerminalSession contracts are unchanged. The UI adapter encodes input UTF-8 to Base64 and interprets metadata.path/shell/exitCode; host has no PTY business interpretation.

Host stream ownership, two per-owner slots including creation, single reader, authorization, presence/lease deadlines and late-create cleanup are generic. New Apps reuse those supported capabilities without host-core business branches. New host permissions/capabilities require explicit composition-root registration, validation and authorization; descriptors alone cannot grant them.

Both reverse transport modules can later join MCP Client (host)/Server (remote) SDKs, but no SDK split is done now. They only depend on SDK/standard libraries and injected transport parameters. `src/reverse/http.ts` HTTP/TLS/proxy policy, `src/transports/reverse.ts` factory/extension/data setup and reconnect, and host auth/management remain integration; no data-protocol interception is hidden in transport.

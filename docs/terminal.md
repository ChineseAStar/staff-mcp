# Terminal app UI

This document describes the source contract on the unmerged, unpublished `feat/mcp-file-manager` branch, not a production deployment or full acceptance report. The authoritative custom protocol is `chat-ai/docs/protocol/terminal.md` in the matching checkout.

`terminal` is an independent, human-operated app enabled with `--extensions terminal` or `--extensions files,terminal`. It requires Linux, a loadable optional `node-pty`, an executable shell, and terminal/data v1 with a usable duplex dataSession. All extensions are disabled by default; apps/data dependencies are derived automatically. Explicit terminal enablement fails startup when the Linux/native PTY/shell prerequisites are unavailable; the default disabled state does not load native PTY code. Local stdio/Docker, direct HTTP and reverse share that public raw HTTP data protocol; standard MCP control transports remain unchanged. The host uses the existing current-chat MCP grant and same-origin browser requests, without a separate terminal permission switch or high-risk confirmation. HTTP/HTTPS follows the site-wide deployment policy, with no terminal-only TLS gate or origin allowlist. HTTPS is recommended for the whole site; HTTP does not encrypt login sessions, tool calls or terminal traffic. Topology and CLI details are in the [README](../README.md). The self-contained HTML Resource is built to `dist/src/terminal/ui/index.html`; terminal bytes do not add model tools, chat messages or chat history.

## Opening and stopping

`--shell` takes an absolute executable file path. Without it, a valid absolute executable `$SHELL` is used; otherwise selection falls back to `/bin/bash`. The shell starts with `-i`, honors normal user startup files and preserves PATH, virtual environments and other staff environment variables. [`src/terminal/pty.ts`](../src/terminal/pty.ts) filters only these exact internal control keys: `STAFF_GLOBAL_DIR`, `STAFF_MCP_IS_DOCKER`, `STAFF_MCP_DATA_BOOTSTRAP`, `STAFF_MCP_DATA_HOST`, `STAFF_MCP_DATA_PORT`, `MCP_REVERSE_URL`, `MCP_REVERSE_TOKEN`, `MCP_REVERSE_NAME`, `MCP_HTTP_TOKEN`, `STAFF_MCP_HTTP_TOKEN`, `STAFF_MCP_REVERSE_TOKEN`. Missing `TERM` becomes `xterm-256color`, and `SHELL` is set to the selected executable. This is not a general secret scrubber or environment sandbox; the same OS identity may still access credentials and other files.

Selecting the Shell App automatically starts one PTY after the host bridge becomes usable; there is no additional open button or high-risk confirmation. The toolbar shows the returned shell and starting path. The PTY defaults to staff's workspace `main`, independently of file-app roots, and inherits staff's environment and OS identity, not a separate browser-user identity; its cwd is not an operating-system sandbox. Shell startup configuration and history are not suppressed, so the remote shell or programs may record content even though chat-ai does not add terminal bytes to chat history.

**清屏** clears only the local terminal display and scrollback; it sends no shell command. Closing the terminal disables input immediately and requests remote cleanup. Closing cannot undo filesystem/network effects and does not guarantee every descendant process has ended. Input, including Ctrl-C and pasted text, goes to the PTY in order; uncertain acknowledgements are never replayed. Normal exit or PTY failure stops the current PTY but preserves the app shell for manual reconnect, not automatic restart.

Hiding the browser page or switching/collapsing app views within the same chat keeps the existing App and PTY. Visibility gates new opening, input and resize requests, not instance identity: already-admitted input, output reads and xterm consumption acknowledgements continue. Returning fits the viewport and enables input on that same PTY, without opening another shell. Genuine host lifecycle/permission loss, chat changes, explicit close, non-BFCache page exit and unmount still fence the instance, discard unsent input and request best-effort cleanup. An actually stopped or failed PTY requires manual reconnect; visibility restoration does not recreate it. Temporary settings loading or catalog-request errors are not confirmed revocation/disconnection. Real lease expiry, grant revocation or connection retirement still fences the PTY. Failed cleanup relies on host cleanup and the remote lease; a disconnected page cannot guarantee that its close request arrived. A pending open may return its terminal ID after the local instance was invalidated, so the host must fence and clean late creation results.

## Host bridge contract

The app uses the existing file-manager UI bridge. It announces `mcp-app-ready` and accepts the parent `mcp-app-connect` v1 handshake with nonce, instance ID, and one MessagePort. Theme snapshots and `{type:'lifecycle', enabled, connected, visible, message?}` use that authenticated port. No browser-direct network, CDN, clipboard API, web-link addon, iframe sandbox relaxation, or extra permission is required. OSC 52 clipboard sequences and OSC 8 hyperlinks are consumed without clipboard access or link activation.

The following are iframe bridge methods, not ordinary app `rpc` calls:

| Method | Params | Result used by UI |
| --- | --- | --- |
| `terminalOpen` | `{rootId?:string,cols:number,rows:number}` | `{terminalId,rootId,path,shell,leaseMs}` |
| `terminalInput` | `{terminalId,data:string}` | acknowledgement only |
| `terminalResize` | `{terminalId,cols,rows}` | acknowledgement only |
| `terminalClose` | `{terminalId}` | acknowledgement only |
| `terminalRead` | `{terminalId,cursor:number}` | next frame from the sustained stream: `{cursor:number,output:string,state:'running'\|'exited'\|'closed',exitCode?:number,outputIncomplete?:boolean,error?:{code:string,message:string}}` |

The browser host opens **`POST /api/mcp/apps/terminals/[terminalId]`** with JSON `{chatId,instanceId}`. The response is sustained `application/x-ndjson; charset=utf-8`, one `MCPAppResponse<MCPTerminalReadResult>` per line: either `{success:true,data:result}` or `{success:false,error:string,code:string}`. Session, Origin/same-site, owner, original app/chat and connection-generation checks still apply. There is one reader per PTY; a second stream cannot take over. Idle terminals emit no periodic empty frames or read requests. Cancelling or losing the stream closes the PTY, without automatic stream resumption or replay. Reverse MCP's SSE control channel is separate from this browser output stream.

`terminalRead` remains only an internal iframe bridge operation that takes the next frame from that same stream. Cursor starts at `0` and is the cumulative UTF-8 byte offset of host-decoded text, not a frame number; subsequent bridge calls use the last safe-integer cursor, only after xterm's write callback. Nonempty running frames advance the cursor; final frames have empty output and retain the last cursor. The browser host then sends `action:"terminalAck"` to `POST /api/mcp/apps`, with `{chatId,instanceId}` and `params:{terminalId,cursor}`, before reading the next frame. There is no HTTP terminalRead action. Only this rendering-consumption ACK releases the delivery and backend data credit: fetch/socket/HTTP enqueue is not consumption. Already-acknowledged cursors do not grant credit twice; an ACK outside the current delivery is rejected. The host owns the shared files/terminal dataSession and incrementally decodes UTF-8 across backend chunks; the iframe receives strings. Each output frame is capped at 64 KiB UTF-8 and the host's output buffer at 256 KiB. Oversized output is an error, not silent truncation.

A final `exited`/`closed` frame is delivered only after preceding output has drained and been acknowledged. EOF alone is not a browser-consumption acknowledgement. Final cleanup releases host ownership and remote resources before another PTY is created; `terminalClose` is idempotent for a terminal belonging to this app instance, including an already-exited terminal. Child exit or a renewal observing final status must not discard buffered output or invalidate the app shell. If remote exit is confirmed before the data stream reaches EOF, input/resize is rejected with `TERMINAL_DRAINING`, not a false success. The host retains the reader; the UI disables new interaction and discards unsent input without replay, but continues the original read/write-callback ACK chain until the actual final frame. Unknown failures, revocation and expiry still stop the session.

The remote terminal status reports detected loss risk as `error:{code:"OUTPUT_INCOMPLETE",message:string}`; it does not have a top-level outputIncomplete field. This is detection and diagnosis, not lossless delivery or recovery of missing bytes. If output may have been lost, the host exposes `outputIncomplete: true` and/or a structured error in the output frame, or emits a failed response frame; it must not translate this condition into a clean EOF. The UI retains rendered text and shows **输出可能不完整** even with exit code `0`, preserving that warning through later lifecycle updates. Stream/read rejection is shown as **输出完整性无法确认**, never a clean-exit claim. Error text is displayed as text, not HTML. An absent flag is not a general guarantee of complete terminal history; local scrollback remains bounded.

Input requests are sequential and small inputs are coalesced within bounded pending storage, each request at most 32 KiB UTF-8 with code-point-safe splitting. Pending UI input including the in-flight request is bounded at 256 KiB; overflow stops the instance instead of silently dropping/replaying input. Backend deliveries can be 64 KiB; staff splits them into ordered, awaited fd writes of at most 32 KiB without decoding arbitrary byte boundaries. Input consumption ACK follows complete fd writes; output ACK follows actual xterm rendering, never fetch/socket enqueue. The common 256 KiB sliding ACK window permits multiple backend blocks in flight, not per-block stop-and-wait; final EOF awaits receiver.end and its ACK, while interruption fails visibly and releases blocked work. Input acknowledgement does not prove command execution.

Only the browser host sends presence every 10 seconds (and at page visibility/restoration changes), without overlapping requests; hidden app views remain eligible and the iframe has no renewal timer. The host server keeps a 120-second browser-presence deadline and uses its existing sweep to renew the unchanged 30-second remote monotonic lease about every 10 seconds, with no overlapping renewal for a PTY. Each renewal rechecks the original authorization and connection; server renewal never extends browser presence. They are real boundaries, not substitutes for the file app's two-hour TTL. BFCache/freeze does not immediately close the instance, but suspension or lost connectivity is not an indefinite detach guarantee: 120-second browser-presence expiry and the shared data channel's 60-second pending-consumption stall timeout still apply. Expired/fenced renewal must reject; already-exited output drains without treating normal exit as grant expiry. The host verifies the original owner/chat/instance/connection and current MCP grant at every boundary and cleans late creates. No iframe-supplied identity replaces those checks.

ResizeObserver fits the local xterm viewport; remote resizes are debounced and ordered. Local display scrollback retains 2000 lines and is not a complete audit log. Terminal output is rendered by xterm, not inserted as HTML. Accessibility mode and the host light/dark semantic palette are enabled.

## Building

With the project's `@xterm/xterm` and `@xterm/addon-fit` dependencies installed:

```sh
npx tsc --project tsconfig.ui.json
node scripts/build-file-manager.mjs
```

The script retains the file-manager build and additionally emits the terminal Resource. It rejects terminal HTML larger than **4 MiB** and embeds both xterm packages' complete LICENSE notices, including dependency copyright, inside the HTML. It does not require external assets at runtime.

For a terminal-only UI check without compiling the server, use `node scripts/build-file-manager.mjs --app terminal --outdir /path/to/scratch`. The output is `/path/to/scratch/terminal/ui/index.html`. App registration, extension negotiation, native PTY packaging, host authorization, and browser/remote lifecycle testing are separate integration responsibilities; a successful UI bundle alone does not verify them.
